# DARI 대화형 신청서 초안 구현

2026년 10월 개편은 신청자의 대화 원문을 보존하면서 신청서에 필요한 정보를 수집하고 한국어 초안을 만드는 데 집중합니다. 번역 검증과 COI 검색은 이번 작성 흐름에 연결하지 않았습니다. 기존 번역·검증 화면은 `LegacyApp.tsx`에 보존했지만 기본 화면에서는 불러오지 않습니다.

## 화면과 결과물

제공된 Design1의 흑백 디자인을 바탕으로 언어 선택, 시작 정보, 대화, 수집 정보 확인, 한국어 초안 화면을 구성했습니다. 한국어 가상 예시 버튼은 고정된 결과를 보여주는 기능이 아니라 실제 모델에 합성 진술을 보내는 기능입니다.

최종 JSON에는 대화 원문, 구조화된 메타데이터, 한국어 초안이 함께 들어갑니다. 원문 메시지에는 고유 ID가 있으며 메타데이터의 인용문과 초안의 문장별 출처를 통해 원문으로 돌아갈 수 있습니다. 사용자가 직접 수정한 초안은 생성 당시 문장과 구분해서 저장합니다.

현재 세션은 메모리에서만 유지되므로 새로고침하거나 앱을 닫으면 사라집니다. 테스트 결과는 내보내기로 보관해야 합니다. 모바일 WebView의 파일 내보내기는 실기기 검증과 네이티브 공유 기능 보완이 필요합니다.

## 대화 엔진

`src/intake`는 UI와 모델 실행 방식에서 독립된 도메인입니다. 기존 신청서 스키마의 134개 필드를 바탕으로 표의 열과 서술형 세부 정보를 분리하고 서명·조력자 확인 항목을 추가했습니다. 현재 전체 목록은 243개이며 14.1~14.3 우선 테스트에는 15개가 포함됩니다. 이 숫자는 필수 질문을 모두 한 번씩 묻는 횟수가 아닙니다. 조건에 따라 적용되는 항목과 수동 확인 항목이 포함돼 있습니다.

전체 모드에서는 모델이 답변과 관련된 문항 범위를 먼저 선택한 뒤 해당 범위의 정보를 추출하고 다음 질문을 작성합니다. 앱은 알려진 요구 항목, 조건과 수집 상태를 관리합니다. 모델이 완료했다고 말하더라도 앱이 이를 신청서 완성으로 간주하지 않습니다.

메타데이터에는 값 외에도 원문 인용, 메시지 ID, 확실성, 직접 경험인지 전해 들은 내용인지, 사용자 확인 여부를 보관합니다. 답변 없음, 모름, 보류, 해당 없음, 충돌을 구분하며 정정은 이전 기록을 삭제하지 않고 대체 관계로 남깁니다. 이름이나 법적 사유를 임의로 추론하거나 폭행 부정을 모든 피해의 부정으로 확대하지 않도록 지시합니다.

초안은 확인된 정보를 문항별로 작성합니다. 모르는 날짜 등은 불확실성을 유지하며 각 문장의 근거를 요구합니다. 인용문이 원문에 존재하는지와 출처 ID는 코드로 검사하지만 의미가 정확하게 보존됐는지까지 입증하지는 못합니다. 따라서 메타데이터와 초안은 사용자가 검토할 후보 결과이며 제출 가능한 법률 문서로 인증된 결과가 아닙니다.

## 모델 실행 경로

- 설치한 Android·iOS 앱은 `OnDeviceLlm` 플러그인을 통해 LiteRT-LM을 호출합니다. 모델이 없거나 실패하면 오류를 표시하며 외부 서버로 자동 전환하지 않습니다.
- 일반 브라우저는 휴대폰 온디바이스 실행이 아닙니다. 작성 원문과 메타데이터를 연결된 개발 서버에 보내고 그 서버의 Ollama가 연산합니다. 기본 모델은 `gemma4:e4b`입니다.
- 브라우저 경로는 JSON 응답 스키마를 전달합니다. 네이티브 경로는 프롬프트로 형식을 지시한 뒤 같은 파서로 검사하므로 형식 오류가 생길 수 있습니다. 오류가 발생해도 원문을 유지하고 재시도할 수 있습니다.

네이티브 설치, 모델 파일 형식과 검증 한계는 [NATIVE_LLM.md](NATIVE_LLM.md)를 참고해 주세요. Ollama 모델 파일은 모바일용 `.litertlm` 파일과 같지 않습니다.

## 개발 실행과 점검

저장소 루트에서 `python3 local_verification_server.py`를 실행하고 `capacitor-web`에서 `npm run dev -- --port 5188 --strictPort`를 실행합니다. Ollama에는 `gemma4:e4b`를 먼저 준비해야 합니다. 브라우저 주소는 `http://127.0.0.1:5188/`이며 서버 API는 기본적으로 `127.0.0.1:8765`입니다.

서버 기본 바인딩은 루프백입니다. 기존 Tailscale 개발 환경을 사용할 때는 필요에 따라 `DARI_BIND_HOST`를 명시하고 방화벽·접근 제어를 별도로 설정해야 합니다. 이 개발 서버에는 인증이 없으므로 실제 신청자의 민감한 진술을 공개 네트워크로 보내는 용도로 사용해서는 안 됩니다.

웹 테스트와 빌드는 `npm test`, `npm run build`로 실행합니다. 루트의 서버 테스트는 `python3 -m unittest discover -s tests -v`입니다. `capacitor-web`에서 `node --experimental-strip-types scripts/smoke-intake.mjs`를 실행하면 가상 진술과 날짜 정정으로 실제 모델 연결을 점검합니다. 테스트 산출물은 Git에서 제외되는 `tmp/`에 저장합니다.

`DARI_TEST_DEMO=1 node --experimental-strip-types scripts/smoke-intake.mjs`는 화면의 한국어 가상 예시와 동일한 원문을 읽어 대화 수집과 초안 작성을 실행합니다. 사용자 확인은 이 가상 테스트 안에서만 명시적으로 모사합니다. 실제 화면에서는 사용자가 수집 내용을 확인해야 초안을 작성할 수 있습니다.

### 실제 모델 시험에서 확인한 한계

최종 웹 화면 시험에서는 가상 예시 입력 후 12개 메타데이터 후보를 수집했고, 확인 단계를 거쳐 14.1~14.3의 한국어 초안을 생성했습니다. 원문·메타데이터·초안을 포함한 JSON 다운로드도 확인했습니다. 이는 해당 한국어 가상 예시의 기능 연결 시험이며 내용 정확도나 실기기 성능의 합격 판정은 아닙니다.

2026-10-06 개발용 Mac의 `gemma4:e4b`로 한국어 가상 사례를 시험했습니다. 초기에는 인용문을 바꾸어 쓰거나 사건 ID와 정정 대상 ID를 누락하는 응답이 나왔습니다. 브라우저 경로의 인용문은 실제 사용자 원문의 문장과 메시지 ID 조합으로 출력 범위를 제한했으며, 사용자가 말하지 않은 ‘미언급’을 ‘모름’으로 기록하는 후보는 채택하지 않습니다. 네이티브에서는 같은 출력 스키마 강제가 연결되지 않아 별도 실기기 시험이 필요합니다.

정정 사례에서는 ‘3월 → 4월’이라는 원문 정정을 모델이 대체 관계로 연결하지 않아 충돌로 남은 경우가 있었습니다. 해당 시험은 정정 처리 성공으로 평가하지 않습니다. ‘폭행·구금은 없었다’는 설명을 전체 피해가 없었다는 응답으로 넓혀 해석하면서 구체적 사건 정보도 함께 내놓은 경우에는 조건 충돌로 표시하고, 사건 정보를 자동으로 버리지 않습니다.

초기 초안이 ‘예’ 한 단어로 끝나거나 일부 사실의 근거 ID를 누락해 거절된 사례도 있었습니다. 현재는 수집 내용 확인을 거친 뒤 모든 입력 사실의 근거 연결을 검사하고, 오류가 있으면 문항별로 한 번만 다시 작성하도록 요청합니다. 재작성도 실패하면 원문과 메타데이터를 보존하고 오류를 표시합니다. 내부 출처 ID를 본문에 쓰는 응답 역시 허용하지 않습니다.

서술형 초안이 생성된 경우에도 원문의 ‘그 뒤’를 ‘이 일 때문에’로 바꾸어 인과관계를 강하게 표현하거나, 대략적인 계절은 남기면서 ‘정확한 날짜는 기억나지 않는다’는 설명을 빠뜨린 사례가 있었습니다. 현재 코드의 출처 연결 검사는 이런 의미 변화를 모두 찾아내지 못하며, 모델의 한 문장 객체에 여러 문장이 담길 수도 있습니다. 한국어 예시의 연결 시험과 243개 목록의 존재를 전체 문항·언어의 내용 정확도 검증으로 해석해서는 안 됩니다.

## 다음 검증 항목

- 최신 Android와 iPhone에서 모델 로딩, 응답 시간, 최대 메모리와 발열을 측정해야 합니다. Android 빌드 성공은 실제 온디바이스 추론 성공과 다릅니다. iOS 전체 빌드에는 Xcode가 필요합니다.
- 언어별 원문 보존, 부정·추측·전언·날짜 정정, 여러 사건의 분리, 누락과 불필요한 재질문을 평가해야 합니다.
- 전체 신청서 목록과 조건은 사회혁신가와 함께 확인해야 합니다. 14.14의 한영 연령 경계 차이는 임의로 결정하지 않고 검토 항목으로 남겼습니다. 서명·동의와 조력자 확인은 모델이 대신 완료하지 않습니다.
- 장시간 작성의 암호화 저장·복구, 모바일 파일 공유, 모델 배포와 업데이트 정책을 정해야 합니다. 실제 신청에 사용하기 전 보안·접근성·내용 정확도 평가가 필요합니다.
