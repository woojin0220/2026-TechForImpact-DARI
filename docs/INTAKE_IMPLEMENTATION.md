# DARI 대화형 신청서 초안 구현

2026년 10월 개편은 신청자의 대화 원문을 보존하면서 신청서에 필요한 정보를 수집하고 한국어 초안을 만드는 데 집중합니다. 번역 검증과 COI 검색은 이번 작성 흐름에 연결하지 않았습니다. 기존 번역·검증 화면은 `LegacyApp.tsx`에 보존했지만 기본 화면에서는 불러오지 않습니다.

## 화면과 결과물

제공된 Design1의 흑백 디자인을 바탕으로 언어 선택 뒤 **시작하기 → 정보 수집 → 대화하기 → 수집 내용 → 한국어 초안**의 다섯 단계로 구성했습니다. 정보 수집과 대화하기는 화면 높이에 고정되고 카드나 채팅창 안에서만 스크롤됩니다. 한국어 가상 예시 버튼은 고정된 결과를 보여주는 기능이 아니라 실제 모델에 합성 진술을 보내는 기능입니다.

최종 JSON에는 대화 원문, 구조화된 메타데이터, 한국어 초안이 함께 들어갑니다. 원문 메시지에는 고유 ID가 있으며 메타데이터의 인용문과 초안의 문장별 출처를 통해 원문으로 돌아갈 수 있습니다. 사용자가 직접 수정한 초안은 생성 당시 문장과 구분해서 저장합니다.

현재 세션은 메모리에서만 유지되므로 새로고침하거나 앱을 닫으면 사라집니다. 테스트 결과는 내보내기로 보관해야 합니다. 모바일 WebView의 파일 내보내기는 실기기 검증과 네이티브 공유 기능 보완이 필요합니다.

## 대화 엔진

`src/intake`는 UI와 모델 실행 방식에서 독립된 도메인입니다. 수집 방식은 신청서 영역에 따라 다릅니다.

| 영역 | 수집 방식 | 코드 |
| --- | --- | --- |
| 1~13번 (인적사항, 가족, 여권, 입국, 체류, 출국) | **폼**. 신청서 단계별로 한 페이지씩 입력하고, 단계를 떠날 때 메타데이터로 저장 | `intake/form.ts`, `FormStage.tsx` |
| 14번 (난민 신청 사유) | **대화로 메타데이터 수집** 후 14번 문항을 계산·작성 | `intake/metadata14.ts`, `intake/derive14.ts` |
| 15번 | 14번 대화 뒤 고정 질문 | `nextStep` |
| 16번, 조력자·제출란 | 모델이 수집하지 않음(직접 서명·확인) | `personal_confirmation` |

### 14번 메타데이터

#### 진술 구조와 문항 간 활용 (metadata schemaVersion 2)

기존 `facts`와 원문은 유지하면서 각 사실에 `statements`를 추가합니다. 각 진술에는 원문 언어의 `subject`(주체), `action`(행동), `object`(대상·내용), `polarity`(긍정·부정·미확정), `certainty`, `knowledge`, `sourceQuotes`가 있습니다. 주체와 대상의 문자열은 해당 원문 인용에 실제로 존재해야 하며 신원이 모호하면 `null`로 남깁니다. 인물의 동일성을 자동 확정하는 별도 인물 DB는 아직 없습니다.

- “그들이 위협했지만 나는 구금되지는 않았고 그들이 경찰인지는 확실하지 않다”는 긍정·부정·불확실한 추측을 각각 나누어 보관합니다. `positive`는 신청자가 그 내용을 진술했다는 뜻이며 실제 사실임을 검증한 상태가 아닙니다.
- 인용이나 역할 문자열이 원문에서 확인되지 않으면 구조화된 진술로 채택하지 않고 `clarification`에 확인할 부분을 표시합니다. 원문은 보존합니다. 이 검사는 출처·형식 검사이며 주체와 대상의 의미상 연결까지 보장하지 않습니다.
- 같은 사실의 `relatedRequirementIds`는 추가로 활용할 서술형 항목을 가리킵니다. 선택지, 예/아니요, 개인정보와 표 항목은 이 연결로 채우지 않습니다. 반복 사건의 항목 충족 여부도 다른 사건에서 가져오지 않습니다. `generateDraft`는 허용된 연결이 있는 사실 ID를 여러 문항에서 인용할 수 있습니다.
- 전체 JSON의 `metadata.statements`는 활성 사실의 개별 진술 목록이고 `questionUses`는 사실과 문항의 연결 목록입니다. `facts`에는 정정 전 이력도 남으며 활성 진술 목록에서는 제외합니다. 철회한 폼 사실 ID는 `withdrawnFacts`에 기록합니다.
- 같은 사건에서 정확히 같은 구조·인용으로 중복 추출한 진술은 `metadata.statements`에서 한 항목으로 모으고 관련 `factIds`를 보관합니다. `questionUses.statementIds`로 문항에서 해당 공통 진술까지 따라갈 수 있습니다. `metadata.events`에는 사건별 미확인 항목과 모른다고 답한 항목을 구분해서 기록하며, 명시적으로 모른다거나 답변을 보류한 항목을 다시 필수 공백으로 만들지 않습니다.
- 정보 확인 화면에서 불확실성·전언·부정 표시를 읽고 “이 내용 확인·정정하기 / Clarify or correct this”를 선택할 수 있습니다. LLM이 해당 진술만 대상으로 질문하며 답변은 같은 사건과 해당 사실의 정정에 연결합니다. 정정 후에는 다시 확인해야 합니다.
- 압축 응답에서도 진술은 `a`, 추가 활용 항목은 `u`로 전달합니다. 사건 ID가 없는 반복 사건 상세는 서로 합치지 않고 채택하지 않습니다. 원문은 남고 해당 항목은 수집 공백으로 유지됩니다.

초안에는 구조화된 진술과 원문 인용을 함께 전달합니다. 기존 응답에 `statements`가 없더라도 읽을 수 있지만 구조를 임의로 만들어내지는 않습니다. 모델·언어별 추출률과 실제 기기의 지연은 추가 측정 대상입니다.

긍정 문장을 모델이 부정으로 표시했는데 인용에 부정 표현이 없는 경우에는 `unspecified`와 확인 필요 상태로 남깁니다. 일부 추측 표현은 불확실성·해석으로 보수적으로 보정합니다. 같은 행위에 관한 상반된 진술은 확인 대상으로 남기되 “위협은 받았지만 구금되지는 않았다”처럼 다른 행위는 별개의 진술로 보관합니다. 이 비교와 다국어 표현 탐지는 휴리스틱이며 의미상의 모든 모순을 찾아내는 검증기는 아닙니다.

14번은 신청서 칸 단위로 묻지 않습니다. 신청인의 이야기를 아래 그룹의 메타데이터로 모은 뒤, 14번 문항을 그 메타데이터에서 채웁니다.

- 한국어 초안 화면은 14.1~14.18을 신청서 순서대로 보여 주는 **수정 가능한 14번 초안**입니다(`buildQuestion14Answers`). 예/아니요·선택·표·날짜는 메타데이터에서, 서술형 칸은 초안 문장에서 채우며, 신청인이 고친 값은 `session.question14`에 저장되어 내보내기와 텍스트 다운로드에 반영됩니다. 메타데이터와 자동 작성 문장·근거는 그대로 보존됩니다.

### 대화 흐름

1. **자유 대화**: 모델이 메타데이터 그룹 중 관련 주제를 고르고(라우팅), 그 범위의 메타데이터를 추출한 뒤 다음 질문 하나를 작성합니다.
2. **"이야기는 여기까지"** 를 누르면 14번은 **질문 대화**로 이어집니다(`nextStep`의 `guided`, `guideConversation`). 앱이 14번 전체에서 아직 빈 정보가 있는 주제를 모으고, 덜 물어본 주제부터 서로 이어지는 주제 묶음(예: 보호 요청·국내 피신·출국, 단체·활동, 증거·신청 경위)을 골라 모델에 넘깁니다. 모델은 그 주제에 대해서만 서식 문구가 아닌 자연스러운 질문 하나를 씁니다. 대화 맥락은 넘기지 않습니다(작은 모델이 이전 질문을 베끼거나 이야기로 되돌아가는 문제 때문).
3. 답변은 항상 14번 전체 메타데이터 범위에서 추출하므로, 질문과 다른 주제를 말해도 해당 주제에 저장되고 그 주제는 다시 묻지 않습니다. 모델의 답장은 짧은 맞장구만 합니다. 같은 주제는 최대 두 번까지 묻고, 이전과 똑같은 질문이 만들어지거나 질문 생성이 실패하면 고정된 중립 문구로 대신 묻습니다. "질문은 여기까지"를 누르면 14번 질문을 마치고 15번만 고정 질문으로 묻습니다.
4. 보완 추출에서 근거 인용에 부정 표현이 없는 "아니요"는 버립니다(언급하지 않은 주제에 "아니요"를 만들어 내는 문제 방지).

모델 응답의 일부가 형식에 맞지 않을 때는 그 턴 전체를 실패시키지 않습니다. 선택지 이름("Political opinion", "예")은 코드로 바꾸고, 그래도 선택지에 없는 값은 저장하지 않아 나중에 다시 묻습니다. 같은 항목·같은 사건이 아닌 정정 대상은 버리고 새 값을 저장하므로, 기존 값과 다르면 "다시 확인 필요"로 표시됩니다.

앱은 알려진 요구 항목, 조건과 수집 상태를 관리합니다. 모델이 완료했다고 말하더라도 앱이 이를 신청서 완성으로 간주하지 않습니다. 한국어 초안은 서술형 메타데이터가 있는 문항만 모델이 작성하고, 14번 선택형·표 칸은 계산 결과로, 1~13번은 "신청서 기재 항목"에 입력값 그대로(선택지는 한국어 선택지명으로) 보여줍니다. 단답형 원문을 한국어로 옮기는 기능은 아직 없습니다.

개발 빌드(`npm run dev`, 또는 `VITE_DARI_DEV_TOOLS=true`로 만든 빌드)의 정보 수집 화면에는 가상 값으로 1~13번을 채우는 "더미 데이터로 자동 채우기"가 있습니다.

메타데이터에는 값 외에도 원문 인용, 메시지 ID, 확실성, 직접 경험인지 전해 들은 내용인지, 사용자 확인 여부를 보관합니다. 답변 없음, 모름, 보류, 해당 없음, 충돌을 구분하며 정정은 이전 기록을 삭제하지 않고 대체 관계로 남깁니다. 이름이나 법적 사유를 임의로 추론하거나 폭행 부정을 모든 피해의 부정으로 확대하지 않도록 지시합니다.

초안은 확인된 정보를 문항별로 작성합니다. 모르는 날짜 등은 불확실성을 유지하며 각 문장의 근거를 요구합니다. 인용문이 원문에 존재하는지와 출처 ID는 코드로 검사하지만 의미가 정확하게 보존됐는지까지 입증하지는 못합니다. 따라서 메타데이터와 초안은 사용자가 검토할 후보 결과이며 제출 가능한 법률 문서로 인증된 결과가 아닙니다.

## 모델 실행 경로

- 설치한 Android·iOS 앱은 `OnDeviceLlm` 플러그인을 통해 LiteRT-LM을 호출합니다. 모델이 없거나 실패하면 오류를 표시하며 외부 서버로 자동 전환하지 않습니다.
- 일반 브라우저는 휴대폰 온디바이스 실행이 아닙니다. 작성 원문과 메타데이터를 연결된 개발 서버에 보내고 그 서버의 Ollama가 연산합니다. 기본 모델은 `gemma4:e4b`입니다.
- 브라우저 경로는 JSON 응답 스키마를 전달합니다. 네이티브 경로는 프롬프트로 형식을 지시한 뒤 같은 파서로 검사하므로 형식 오류가 생길 수 있습니다. 오류가 발생해도 원문을 유지하고 재시도할 수 있습니다.

네이티브 설치, 모델 파일 형식과 검증 한계는 [NATIVE_LLM.md](NATIVE_LLM.md)를 참고해 주세요. Ollama 모델 파일은 모바일용 `.litertlm` 파일과 같지 않습니다.

## 개발 실행과 점검

저장소 루트에서 `python3 local_verification_server.py`를 실행하고 `capacitor-web`에서 `npm run dev -- --port 5188 --strictPort`를 실행합니다. Ollama에는 `gemma4:e4b`를 먼저 준비해야 합니다. 브라우저 주소는 `http://127.0.0.1:5188/`이며 서버 API는 기본적으로 `127.0.0.1:8765`입니다.

서버는 루프백(`127.0.0.1`)에만 바인딩하며 외부 네트워크 바인딩 옵션은 제공하지 않습니다. 이 개발 서버에는 인증이 없으므로 실제 신청자의 민감한 진술을 네트워크로 보내는 용도로 사용해서는 안 됩니다.

웹 테스트와 빌드는 `npm test`, `npm run build`로 실행합니다. 루트의 서버 테스트는 `python3 -m unittest discover -s tests -v`입니다. `capacitor-web`에서 `node --experimental-strip-types scripts/smoke-intake.mjs`를 실행하면 가상 진술과 날짜 정정으로 실제 모델 연결을 점검합니다. 테스트 산출물은 Git에서 제외되는 `tmp/`에 저장합니다.

`DARI_TEST_DEMO=1 node --experimental-strip-types scripts/smoke-intake.mjs`는 화면의 한국어 가상 예시와 동일한 원문을 읽어 대화 수집과 초안 작성을 실행합니다. 사용자 확인은 이 가상 테스트 안에서만 명시적으로 모사합니다. 실제 화면에서는 사용자가 수집 내용을 확인해야 초안을 작성할 수 있습니다.

### 실제 모델 시험에서 확인한 한계

최종 웹 화면 시험에서는 가상 예시 입력 후 12개 메타데이터 후보를 수집했고, 확인 단계를 거쳐 14.1~14.3의 한국어 초안을 생성했습니다. 원문·메타데이터·초안을 포함한 JSON 다운로드도 확인했습니다. 이는 해당 한국어 가상 예시의 기능 연결 시험이며 내용 정확도나 실기기 성능의 합격 판정은 아닙니다.

2026-10-06 개발용 Mac의 `gemma4:e4b`로 한국어 가상 사례를 시험했습니다. 초기에는 인용문을 바꾸어 쓰거나 사건 ID와 정정 대상 ID를 누락하는 응답이 나왔습니다. 브라우저 경로의 인용문은 실제 사용자 원문의 문장과 메시지 ID 조합으로 출력 범위를 제한했으며, 사용자가 말하지 않은 ‘미언급’을 ‘모름’으로 기록하는 후보는 채택하지 않습니다. 네이티브에서는 같은 출력 스키마 강제가 연결되지 않아 별도 실기기 시험이 필요합니다.

정정 사례에서는 ‘3월 → 4월’이라는 원문 정정을 모델이 대체 관계로 연결하지 않아 충돌로 남은 경우가 있었습니다. 해당 시험은 정정 처리 성공으로 평가하지 않습니다. ‘폭행·구금은 없었다’는 설명을 전체 피해가 없었다는 응답으로 넓혀 해석하면서 구체적 사건 정보도 함께 내놓은 경우에는 조건 충돌로 표시하고, 사건 정보를 자동으로 버리지 않습니다.

초기 초안이 ‘예’ 한 단어로 끝나거나 일부 사실의 근거 ID를 누락해 거절된 사례도 있었습니다. 현재는 수집 내용 확인을 거친 뒤 모든 입력 사실의 근거 연결을 검사하고, 오류가 있으면 문항별로 한 번만 다시 작성하도록 요청합니다. 재작성도 실패하면 원문과 메타데이터를 보존하고 오류를 표시합니다. 내부 출처 ID를 본문에 쓰는 응답 역시 허용하지 않습니다.

서술형 초안이 생성된 경우에도 원문의 ‘그 뒤’를 ‘이 일 때문에’로 바꾸어 인과관계를 강하게 표현하거나, 대략적인 계절은 남기면서 ‘정확한 날짜는 기억나지 않는다’는 설명을 빠뜨린 사례가 있었습니다. 현재 코드의 출처 연결 검사는 이런 의미 변화를 모두 찾아내지 못하며, 모델의 한 문장 객체에 여러 문장이 담길 수도 있습니다. 한국어 예시의 연결 시험과 243개 목록의 존재를 전체 문항·언어의 내용 정확도 검증으로 해석해서는 안 됩니다.

### 14번 메타데이터 구조 시험 (2026-10-06, `gemma4:e4b`, 개발용 Mac)

- 기존 시험 시나리오(정치적 의견, 3월 → 4월 정정)는 통과했습니다. 정정은 대체 관계로 연결됐고, 신청 사유 요약에 사건 상세를 넣지 않도록 바꾼 뒤 14.1·14.3 초안에 정정 전 날짜가 남지 않았습니다. 응답 시간은 대화 턴당 35~51초(라우팅 포함), 초안은 문항당 5~14초였습니다.
- 사건 2개와 가족 피해 1건을 말한 전체 흐름 시나리오에서 `harm-1`, `harm-2`, `family_harm-1`로 사건이 분리됐고, 시점·장소·행위자·석방 경위가 각 사건에 맞게 들어갔습니다. 입국일로 늦은 신청 여부도 계산됐습니다.
- 남은 오류: 두 번째 사건의 폭행이 첫 사건의 피해 유형에도 들어갔고, 신청인이 이유를 모른다고 한 사건에도 "종교"가 이유로 들어갔습니다. 장소를 더 구체적으로 다시 말한 경우(“제 집” → “가상의 도시 A에 있는 제 집”) 모델이 정정으로 표시하지 않아 충돌로 남았으며, 초안 모델은 충돌 값을 원문에서 다시 가져와 쓰기도 했습니다. 사건 간 정보 혼입과 추정 기록은 수집 내용 확인 단계에서 신청인이 바로잡아야 합니다.
- 한 번의 시험이며 정확도 평가가 아닙니다. 휴대폰 온디바이스 실행에는 출력 형식 강제가 없어 결과가 다를 수 있습니다.

### 추출 개선 후 시나리오 채점 (2026-10-07)

`scripts/run-intake-scenarios.mjs`의 10개 시나리오(48개 검사) 기준 34/48 → **47/48**. 바꾼 점:

- 주제 선택(라우팅) 호출을 없애고 14번 메타데이터 전체를 간결한 형태로 매번 전달합니다. 잘못 고른 주제 때문에 피해가 활동으로 들어가거나 정정이 다른 칸에 들어가던 문제가 사라졌습니다.
- 답변이 언급한 주제를 묻는 짧은 확인 호출을 추가하고, 언급됐지만 추출되지 않은 주제(최대 2개)는 그 주제만 다시 추출합니다.
- 코드 보정: 다중 선택 값은 합치고, 더 구체적으로 다시 말한 값은 갱신하며, "기억나지 않음"은 모름으로, "아니라/잘못 말했다" 같은 명시적 정정은 이전 값을 대체합니다. 상세 내용이 있으면 해당 그룹의 예/아니요를 같은 인용으로 채웁니다.
- 이후 추가 개선: 답변이 길거나 여러 문장인데 한 주제만 추출됐을 때만 주제 확인 호출을 하고(속도), 상세가 있으면 예/아니요를 같은 인용으로 채우며, 모델이 정정 값을 충돌로 보내도 명시적 정정이면 대체합니다.
- 초안: 원문 메시지 전체 대신 확인된 사실과 그 인용만 보내고, 정정된 옛 값 목록을 함께 전달해 초안에 남으면 한 번 다시 쓰게 합니다. 문장 수(20)·길이(400자)를 제한해 반복 생성으로 시간이 초과되던 문제를 막았고, 다시 써도 빠진 사실이나 옛 값이 남으면 초안 전체를 실패시키지 않고 화면에 "확인 필요"로 표시합니다.
- 최종 채점(2026-10-07): **54/54** (메타데이터 48개 + 초안 6개). 실행마다 결과가 달라질 수 있습니다.
- 속도: 개발용 Mac에서 시나리오(1~2턴)당 약 30초~2분, 초안을 포함하면 2~6분이었습니다. 같은 Mac에서도 메모리 상황에 따라 2~3배 차이가 났습니다. 휴대폰 속도는 실기기에서 측정해야 합니다. 앱은 모델이 이전 요청을 처리 중이면 끝날 때까지 기다렸다가 다시 시도합니다.

### 긴 작성 흐름 개선 (2026-10-24)

- 대화 화면의 `More` 메뉴에서 현재 주제와 전체 주제 목록을 확인합니다. 전체 항목 개수를 완료율로 보이게 하던 표시를 주제별 상태로 대체했습니다. 안내·보류·내용 확인 버튼은 기본 화면에서 접어두며 메뉴는 대화 위에 겹쳐 열려 채팅 영역을 줄이지 않습니다.
- 자유 이야기를 마치면 부족한 부분의 추가 질문으로 이동합니다. 추가 질문에서 `모름`·`나중에 답하기`를 선택하면 현재 질문의 주제만 넘깁니다. `topicDecisions`에 선택을 기록하며 개별 항목에 가짜 답변을 생성하거나 누락을 해결된 것으로 표시하지 않습니다. 질문 전체를 마치고 검토로 이동할 수도 있습니다. 미전송 입력이 있으면 이동 버튼을 비활성화합니다.
- 확인 화면은 주제·사건별 수집 내용을 우선 표시합니다. 새로운 요약을 생성하지 않고 수집된 값을 표시하며 불확실성·전언·추정 표기를 유지합니다. 개별 수정과 묶음별 확인이 가능하고 상세 메타데이터·원문은 펼쳐서 봅니다. 확인은 정보 ID에 연결되므로 새로운 정보는 다시 확인해야 합니다.
- 초안 하단에서 미답변·모름·보류·충돌 항목과 저장 파일의 차이를 안내합니다. 영어 확인본이 준비돼야 의미 확인을 표시할 수 있고 초안 수정 후 확인 표시가 해제됩니다. 확인 전에도 작업 중인 파일 저장은 허용합니다. JSON의 `applicantReview`는 사용자의 의미 확인 표시이며 법률 검토·자동 검증·제출 완료가 아닙니다.
- 이번 추가 UI 문구는 한국어·영어 기준입니다. 다른 언어의 신규 안내는 영어로 표시하며 기존 언어별 대화와 답변은 유지합니다. 영어 이외의 언어로 초안을 역번역하는 기능, 장기 저장과 복원은 이번 범위에 포함하지 않았습니다.
- 회귀 시험: `tests/journey.test.mjs`에서 주제 보류 시 원문 보존·누락 유지, 사건 분리, 새 정보의 확인 해제, 정정 전 정보 제외와 테스트 범위를 검사합니다.
- 브라우저 연결 시험: 영어 가상 사례에서 주제 보류 → 사건별 검토 → 묶음 확인 → 한국어 초안과 영어 확인본 → 의미 확인 → 초안 수정에 따른 확인 해제 → 전체 기록 다운로드 요청 안내까지 확인했습니다. 자동 시험 106개와 웹 빌드가 통과했습니다. 전체 양식의 장시간 완주나 실기기 시험은 아닙니다. 가상 사례의 안내 문구가 신청 사유로 추출되고 일부 진술이 초안에서 빠진 경우가 있어 모델의 내용 정확도가 검증되었다고 해석해서는 안 됩니다.
