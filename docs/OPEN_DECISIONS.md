# DARI 향후 논의·결정 사항

## 1. 지원 언어

현재 러시아어·아랍어·프랑스어·페르시아어는 데모 선택지일 뿐 우선 지원 언어로 확정되지 않았습니다. 언어를 먼저 늘리기보다 초기 1~2개 언어에서 정확성과 사용성을 검증하는 편이 적절합니다.

### 결정 기준

- 국내 난민 신청자의 실제 사용 언어와 대상 규모
- 공익법센터가 자주 지원하는 언어
- 공인 통역가나 검수자를 확보할 수 있는지
- 신청서 공식 문항 번역본을 만들고 유지할 수 있는지
- 번역 모델의 해당 언어 품질과 문자 입력 편의성
- 방언·문어·구어 차이를 얼마나 다뤄야 하는지

### 확인할 내용

- 최근 상담·신청 사례에서 언어별 수요 집계
- 언어별 실제 진술문 30~50개와 전문가 기준 번역 확보 가능 여부
- 오른쪽에서 왼쪽으로 쓰는 언어의 UI와 키보드 테스트
- 한 사람이 여러 언어를 섞어 쓰는 경우의 처리 방식

### 우선 결정 질문

1. 첫 현장 검증 언어를 하나만 고른다면 무엇인가요?
2. 언어 선정 기준을 신청자 수, 지원기관의 업무량, 검수자 확보 중 어디에 둘 것인가요?
3. 신청자가 선택한 언어와 실제 입력 언어가 다를 때 자동 감지할 것인가요?

## 2. 번역 경로와 한국어본의 역할

현재 경로는 `선택 언어 → 영어 → 한국어`입니다. 영어 신청서가 중심 산출물이기 때문에 구현이 단순하지만, 영어 오류가 한국어에 전파되고 한국어 문장이 어색해질 수 있습니다.

| 선택지 | 구조 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. 현재 방식 | 원문→영어→한국어 | 영어본과 한국어본의 내용 흐름이 같고 구현이 단순함 | 영어 오류가 한국어에 그대로 전파됨 |
| B. 독립 번역 | 원문→영어, 원문→한국어 | 한국어가 영어 오류를 독립적으로 확인하는 보조 수단이 될 수 있음 | 두 번역이 다를 때 어느 쪽이 맞는지 추가 판단 필요 |
| C. 서버 고품질 번역 | 원문을 서버 모델로 영어·한국어 번역 | 더 큰 모델과 용어 사전을 사용할 수 있음 | 민감정보 전송, 비용, 네트워크 의존성 증가 |
| D. 혼합 방식 | 기기 번역 후 위험 문장만 서버 또는 사람 검토 | 개인정보와 품질 사이의 균형 가능 | 흐름과 운영 기준이 복잡해짐 |

### 제안할 실험

같은 원문으로 A와 B를 모두 생성하고 전문가가 의미 보존, 자연스러움, 핵심 사실 오류를 문장별로 평가합니다. 영어본은 신청서 초안, 한국어본은 확인용이라는 역할을 유지하며 한국어를 영어 검증의 근거로 자동 사용하지 않습니다.

### 평가 항목

- 날짜·숫자·인명·지명 보존
- 부정·추정·불확실성 보존
- 행위자와 피해자의 관계 보존
- 사건 순서와 인과관계 보존
- 피해·위협 강도의 과장 또는 축소
- 문장 자연스러움과 사용자의 이해 가능성

## 3. 검증 모델과 서버

현재는 16GB Mac에서 Ollama로 Qwen3 4B와 Llama 3.2 3B를 실행합니다. 이는 개발 테스트용 구성입니다.

### 서버 선택지

| 선택지 | 적합한 단계 | 장점 | 고려할 점 |
| --- | --- | --- | --- |
| 개발자 Mac | 초기 프로토타입 | 비용이 적고 데이터가 외부로 나가지 않음 | 성능·가용성·협업에 한계 |
| 기관 내부 GPU 서버 | 현장 파일럿 | 데이터 통제와 더 큰 모델 사용 가능 | 장비·운영·보안 담당 필요 |
| 국내 클라우드 전용 서버 | 확장 테스트 | 접근성과 운영 자동화 | 계약, 저장 위치, 비용, 로그 정책 필요 |
| 상용 외부 API | 비교 실험 | 높은 품질과 빠른 도입 | 민감정보 처리와 서비스 약관 검토 필요 |

### 모델 선정 기준

- 러시아어·아랍어·페르시아어 등 대상 언어의 의미 비교 성능
- 구조화 JSON 출력 준수율
- 누락·부정 반전·행위자 변경 탐지율
- 유리·불리 방향 분류의 일관성
- 같은 입력을 반복했을 때 결과 안정성
- 추론 시간, 메모리, 동시 사용자 수
- 라이선스와 상업·공익 서비스 이용 조건

모델명부터 정하기보다 같은 익명화 평가셋으로 후보 모델을 비교한 뒤 선택해야 합니다.

## 4. 개인정보 마스킹

현재 정규식 마스킹은 프로토타입 수준이며 국가별 식별정보를 다루기에 부족합니다. 특히 사건 날짜와 생년월일을 구분하지 않고 숫자 형태만 보면 검증에 필요한 정보를 지울 수 있습니다.

### 제안하는 처리 단계

1. 기기에서 이메일·전화번호·명백한 식별번호 후보를 탐지합니다.
2. 이름·주소·기관·여권번호 등은 다국어 개체명 인식으로 후보를 표시합니다.
3. 같은 대상을 `[PERSON_1]`, `[ADDRESS_1]`처럼 일관된 토큰으로 치환합니다.
4. 사건 날짜는 원칙적으로 유지하고 생년월일은 별도 후보로 분류합니다.
5. 사용자가 실제 전송본을 확인하고 수정합니다.
6. 서버는 원문 저장과 내용 로그를 남기지 않습니다.

### 반드시 결정할 내용

- 개인정보와 검증 필수정보의 경계
- 생년월일·사건일·출입국일의 처리 차이
- 사람 이름과 단체·정부기관 이름의 처리 차이
- 국가별 신분증·여권·난민신청 관련 번호 규칙
- 자동 삭제, 후보 강조, 사용자 승인 중 기본 동작
- 마스킹 전 원문을 기기에 임시 저장할지와 삭제 시점

## 5. 더 체계적인 검증 방식

단일 프롬프트 호출만으로는 누락과 오탐을 관리하기 어렵습니다. 다음과 같은 다단계 구조를 검토할 수 있습니다.

### 제안 파이프라인

1. **형식 검사:** 문항 번호, 빈 답변, 길이, 숫자·날짜·고유명사 후보를 기기에서 추출합니다.
2. **문장 정렬:** 원문과 영어 번역문을 문장 또는 의미 단위로 연결합니다.
3. **규칙 기반 비교:** 숫자, 날짜, 부정어, 빈도 표현, 문항 누락을 우선 검사합니다.
4. **LLM 의미 비교:** 정렬된 문장별로 유형·방향·심각도와 근거 발췌를 생성합니다.
5. **2차 판정:** 심각도 ‘높음’이나 모델 간 불일치만 다른 모델 또는 별도 프롬프트로 재검토합니다.
6. **전체 일관성 검사:** 문항 사이의 사건 순서와 인물 관계 모순을 별도로 확인합니다.
7. **사용자·전문가 확인:** 원문과 번역문을 나란히 보여 수정 또는 검토 요청으로 연결합니다.

### 검증 결과에 필요한 상태

- 이상 없음
- 자동 수정 없이 사용자 확인 필요
- 통역가 검토 권장
- 번역 재생성 권장
- 시스템이 판단할 수 없음

모델이 번역을 자동으로 고치기보다 문제 위치와 이유를 제시하고, 수정은 원문 작성자나 통역가의 확인 뒤 이루어져야 합니다.

### 평가셋 설계

정답 번역만 모으는 것으로는 부족합니다. 원문과 정상 번역 쌍에 다음 오류를 의도적으로 하나씩 삽입한 대조군이 필요합니다.

- 한 문장 또는 제한 조건 누락
- 존재하지 않는 피해·무기·동기 추가
- 부정 반전
- 가능성·추정이 확정 사실로 변함
- 가해자와 피해자 뒤바뀜
- 날짜·빈도·기간 변경
- 인과관계 추가
- 피해 강도 강화 또는 약화
- 원문에 없는 법률 용어 추가

각 사례에는 오류 유형, 방향, 심각도, 정확한 위치를 전문가가 표시합니다. 모델별로 유형 탐지 재현율, 오탐률, 방향 정확도, JSON 준수율, 처리 시간을 측정합니다. 특히 심각도 높은 오류의 미탐률을 핵심 지표로 두는 것이 적절합니다.

## 6. 권장 논의 순서

1. 현장 검증 대상 언어 1개와 검수자 확보 여부 결정
2. 영어본·한국어본의 역할과 번역 경로 A/B 실험 결정
3. 익명화된 평가 문장과 의도적 오류 사례 제작
4. 개인정보 분류표와 사건 날짜 처리 원칙 결정
5. 다단계 검증 파이프라인의 최소 범위 결정
6. 같은 평가셋으로 모델·서버 후보 비교
7. 현장 파일럿의 전문가 개입 지점과 책임 범위 결정
