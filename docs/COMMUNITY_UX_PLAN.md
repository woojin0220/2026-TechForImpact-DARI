# DARI 커뮤니티: 벤치마킹과 1차 개발 범위

검토일: 2026-11-26 / 작업 브랜치: feat/community-ux

## 1. 결론

**질문과 경험을 모국어로 나누고, 필요한 정보를 다시 찾을 수 있는 게시판형 커뮤니티.**

외국인을 하나의 사용자군으로 묶어 특정 앱에 익숙하다고 가정하지 않는다. 아래는 서비스의 실제 기능을 비교한 결과이며, 대상 난민신청자의 이용 앱·선호 언어·읽기 능력에 대한 검증은 별도 필요하다. 기존 3명 설문만으로 선호 인터페이스나 커뮤니티 수요 규모를 확정하지 않는다.

실시간 채팅보다 글 단위로 질문·답변을 보존하는 구조를 우선 제안한다. 이유는 정보 재탐색, 번역·원문 대조, 신고 대상 특정, 운영자의 답변 축적이다. 이것은 DARI의 제품 판단이며 비교 서비스의 우월성 순위가 아니다.

## 2. 무엇을 가져올 것인가

| 비교 서비스 | 확인한 구조·특징 | DARI에 적용할 요소 | 그대로 가져오지 않을 요소 |
| --- | --- | --- | --- |
| Reddit | 주제별 커뮤니티, 글·댓글 검색, 투표 | 제목 중심 목록, 검색, 글 단위 댓글 | 비추천·인기 경쟁, 깊은 댓글 트리. 추천 수를 사실의 정확도로 표시하지 않음 |
| Facebook Groups | 그룹별 대화, 공개 범위, 관리자·참여 관리 | 누가 글을 볼 수 있는지 안내, 운영 책임 명시 | 공개 범위가 모호한 경험, 개인 프로필을 과도하게 노출하는 구조 |
| WhatsApp Communities | 관련 그룹 묶기, 공지 그룹, 공지에 대한 정리된 답글 | 공지와 회원 대화의 역할 분리, 간단한 참여 흐름 | 실시간 대화방을 기본 화면으로 두는 구조. DARI는 정보를 다시 찾는 용도 우선 |
| Discourse | 분류·검색, 신뢰 체계, 해결된 질문의 지식 축적 | 운영자가 반복 질문을 정리, 향후 질문 해결 상태 도입 검토 | 활동량 기반 등급을 법률 지식·정확성의 인증으로 사용하는 방식 |
| 네이버 카페 | 운영자가 구성하는 게시판, 카페 검색 | 적은 수의 게시판, 공지의 지속적 접근성 | 복잡한 가입·등업·다단계 메뉴 |
| 당근 동네생활 | 생활 질문과 일상 경험 공유, 신고·차단 | 짧고 구체적인 생활 질문, 가벼운 목록, 도움을 주는 댓글 | 실제 거주 위치 인증·공개를 필수 참여 조건으로 삼는 방식 |
| Blind | 직장 인증과 익명 대화의 결합 | 공개 닉네임과 내부 계정을 구분, 기관 역할 표시는 검증 절차와 연결 | 난민 신분·국적 증명을 커뮤니티 기본 참여 조건으로 요구하는 방식 |
| 디시인사이드 | 관심 주제별 갤러리, 개설자 운영 | 제목 중심의 빠른 목록 탐색만 참고 | 수많은 하위 게시판·인기 순위·복잡한 용어를 초기 서비스에 적용하는 방식 |

## 3. DARI의 정보 구조

**커뮤니티는 경험 공유, 스케줄러는 출처가 있는 절차 안내, 신청서는 비공개 작성.** 신청서·일정·박해 진술을 커뮤니티로 자동 공개하거나 글쓰기의 기본값으로 가져오지 않는다.

| 화면 | 먼저 보여줄 정보 | 주요 행동 | 부가 행동 |
| --- | --- | --- | --- |
| 목록 | 질문·생활정보·공지 탭 → 검색 → 제목·본문 일부·작성 시점·댓글 수 | 글 열기, 글쓰기 | 게시판 이동·계정 |
| 글 상세 | 제목 → 닉네임·작성 시점 → 원문/번역 → 본문 → 댓글 | 읽기·댓글 쓰기 | 도움됐어요·신고·차단·본인 글 관리 |
| 글쓰기 | 게시판 → 제목 → 내용 → 게시 버튼 | 글 작성·게시 | 민감정보 확인, 취소 시 작성 내용 처리 |
| 공지 | 기관이 게시한 공지 목록과 게시 주체 | 공지 읽기 | 필요 시 공식 안내 출처 열기 |

초기에는 기존 3개 게시판을 유지한다. 인원이 적은 상태에서 국가·언어·도시별로 나누면 빈 게시판이 늘 수 있으므로 이용량과 요청을 확인한 뒤 분리한다. 기관 공지는 정부의 공식 결정과 동일한 의미가 아니며, 기관 배지가 개별 글 내용의 사실 검증을 뜻하지도 않는다.

디자인 원칙: 흰 배경·검정 본문·절제된 회색 보조 정보, 제목 우선, 목록의 반복 카드 테두리·그림자 축소, 텍스트가 있는 행동 버튼, 충분한 터치 영역, RTL·긴 언어에서 가로 넘침 방지. 앱 전체 디자인 체계를 유지한다.

## 4. 이번에 구현하는 범위

1. 게시판 내 제목·본문 **원문 검색**: 서버가 접근 가능한 글을 필터링한 뒤 페이지 단위 반환. 현재 불러온 20개만 검색하는 방식이 아님. 언어 간 의미 검색은 포함하지 않음.
2. 답변 없는 질문 필터와 최신 글 표시는 후속 사용자 피드백에 따라 제거. 첫 방문 안내·내 활동·본인 글 수정·댓글 초안은 `COMMUNITY_EXPERIENCE_2026-11-26.md` 참조.
3. 제목 중심의 평평한 목록과 검색 결과 없음·초기화·추가 로딩 실패 안내.
4. 탭/검색을 빠르게 바꿨을 때 이전 응답이 새 목록을 덮어쓰지 않도록 처리. 더 보기 중복 요청 방지, 추가 로딩 실패 시 기존 글 보존.
5. 6개 언어 문구와 로컬 Supervisor 데이터에 동일한 탐색 기능 적용.

기존 댓글·번역·신고·차단·권한 구조는 유지. 새 DB 스키마는 추가하지 않음. 검색은 기존 post_feed와 기존 사용자 권한을 통해 조회. 운영 DB의 RLS가 올바른지는 별도의 실제 통합 시험 대상.

## 5. 배포 전 필수 작업 — 이번 구현 완료와 구분

| 영역 | 확인할 사항 | 완료 증거 |
| --- | --- | --- |
| 권한 | 다른 계정의 글 수정·삭제 불가, 차단/숨김 글과 개인정보 비노출, 일반 회원 공지 작성 불가 | 실제 테스트용 Supabase와 2개 이상 계정으로 접근 시험 |
| 운영 | 신고를 누가 어디에서 확인하고 처리할지, 문의·삭제 요청·이의 제기 경로 | 담당자·관리 화면·처리 절차 확정 및 신고 1건 끝까지 처리 |
| 작성 | 오게시·연속 클릭·실패 재시도, 수정·취소 시 내용 보존, 민감정보 확인 | 실기기 작성→게시→관리 시나리오. 본인 글 수정 UI 구현, 실계정 접근 검증은 별도 |
| 번역 | 실제 기기에서 지원 언어, 실패·원문 전환, 서버 전송 여부 안내 | 실제 번역 엔진 실행과 네트워크 확인. Supervisor도 준비된 기기·로컬 번역기 연결, 미연결 시 원문 표시 |
| 탐색 | 원문 검색의 특수문자, 차단된 글 제외, 페이지 경계, 검색 성능 | 실제 PostgREST 검색, 동일 시각 글의 페이지 경계 검증. 기존 시각 단독 커서는 별도 개선 필요 |
| 유입·답변 | 처음 들어왔을 때 읽을 만한 내용과 답변할 사람이 있는지 | 출처 있는 공지·동의 받은 경험 글 준비, 초기 답변 담당자 지정. 가상 글을 실제 경험으로 게시하지 않음 |

운영 목표는 단순 게시글 수보다 **질문을 찾을 수 있었는지, 답변을 받았는지, 다시 방문할 이유가 생겼는지**로 설정한다. 첫 답변까지 시간·무응답 질문 비율·검색 후 글 열기·신고 처리 시간을 계측하되, 목표 수치는 실제 소규모 테스트 후 결정한다. 진술 내용 자체를 분석 로그에 남기는 방식은 피한다.

## 6. 다음 사용자 검증

대상자에게 익숙한 앱을 먼저 묻고, 설명 없이 ① 특정 생활 정보를 찾기 ② 질문 작성 ③ 답변 확인 ④ 원문 보기 ⑤ 신고하기를 수행하도록 관찰한다. 클릭 수보다 막히는 위치·언어 이해·공개 범위에 대한 이해를 기록한다. 인터페이스 친숙도와 커뮤니티 이용 의향은 서로 구분한다.
